# TypeMore — Бэкенд: стек и архитектура

## 0. Стек

| Слой             | Выбор                                                            |
| ---------------- | ---------------------------------------------------------------- |
| Язык             | Go (один статический бинарь, отличные WebSocket, простой деплой) |
| БД               | PostgreSQL — источник истины                                     |
| Кэш / read-model | Redis — лидерборды (ZSET), сессии, rate limiting                 |
| Очередь          | river — **пока не нужен**: replay-воркер берёт работу из `runs` через `FOR UPDATE SKIP LOCKED` (docs/REPLAY.md) |
| Replay ядра      | goja (JS-интерпретатор на Go) исполняет бандл TS-ядра            |
| Деплой           | docker compose (app + postgres + redis) на VPS                   |

## 1. Ключевое решение: единое ядро без дрейфа

Античит и скоринг стоят на серверном replay event-логов, а ядро (редьюсер,
mulberry32, FNV-1a, метрики) написано на TypeScript.

**Решение: сервер исполняет тот же JS-бандл ядра через goja.**
Ноль дрейфа, ноль переписываний. Replay асинхронный (очередь) — скорость
интерпретатора некритична до тысяч забегов в минуту.

**План Б (если упрёмся в производительность):** порт ядра на Go +
**golden-вектора** в CI — из vitest-сьюта генерятся JSON-файлы
(сид + лог событий → ожидаемое состояние + метрики), Go-тесты прогоняют
те же вектора. Разошлись — CI красный. Клиентское TS-ядро при этом не трогаем.

**Отвергнуто: Go-ядро + WASM в браузер.** Двойное переписывание (ядро + вся
клиентская интеграция), бандл-налог рантайма Go (мегабайты; TinyGo — свои
ограничения), боль на границе JS↔WASM при по-кейстроковом чтении состояния
рендером, деградация DX. Не даёт ничего сверх goja/golden-векторов.

## 2. Модульный монолит

Один бинарь. Никаких микросервисов. Пакеты режем по доменам, чтобы потом
можно было вынести кусок (реально понадобится максимум для match).

```
typemore-server/
├── cmd/
│   └── server/
│       └── main.go          # сборка приложения, DI руками
├── internal/
│   ├── platform/            # инфраструктура: db (pgx), redis, config,
│   │                        # http-middleware, logger — не знает о доменах
│   ├── auth/                # OAuth (GitHub/Google), opaque-сессии
│   ├── runs/                # приём забегов, хранение immutable-логов
│   ├── replay/              # goja + бандл ядра, реестр словарей, воркер валидации
│   ├── score/               # формулы scoreV1 / tpV1 — версионированные чистые функции
│   ├── leaderboard/         # бакеты, Redis ZSET, rebuild из Postgres
│   ├── rating/              # TP: топ-100, decay, дедуп по бакету, пересчёт
│   ├── wordgen/             # выдача сидов, dict-хэши (FNV-1a), star rating, daily
│   ├── anticheat/           # эвристики поверх replay, флаги, shadow-ban
│   ├── admin/               # ревью flagged-забегов
│   └── match/               # (позже) комнаты, WS-релей input-событий
├── db/
│   └── migrations/          # goose
├── sqlc.yaml                # генерация типобезопасного кода из SQL
└── docker-compose.yml
```

Правила слоёв:

- `platform` не импортирует домены.
- Домены не импортируют друг друга напрямую — общаются через интерфейсы,
  объявленные у потребителя (идиоматичный Go).
- HTTP/WS-хендлеры тонкие, вся логика в доменных пакетах.

## 3. Поток данных забега

```
клиент завершил ран
  → POST /runs (event-лог, сжатый) + локально посчитанный превью-результат
  → структурная проверка (размер, формат)
  → лог в Postgres как immutable blob, статус pending
  → клиенту — мгновенный ответ с превью; ран остаётся `pending`
воркер:
  → replay лога через goja (тот же код, что у клиента)
  → пересчёт метрик и score версионированной формулой
  → сверка с клиентскими цифрами
  → эвристики античита (распределение межнажатийных интервалов,
    слишком ровный тайминг, невозможные скорости)
  → статус accepted | flagged | rejected  (таблица решений — docs/REPLAY.md)
accepted:
  → апдейт бакетного ZSET в Redis
  → инкрементальный пересчёт TP профиля
```

**Очередь — не river.** Один тип джобы поверх колонки, которая и так
проиндексирована (`runs_pending_idx`): claim, все решения и commit живут в
ОДНОЙ транзакции, поэтому нет статуса `processing`, нет джанитора, а упавший
воркер откатывается ровно в `pending`. Обоснование и цена (длительность
транзакции) — docs/REPLAY.md. river вернётся, когда появятся расписания
(daily challenge, ночные пересчёты).

**Принцип: Postgres — источник истины, Redis — перестраиваемый read-model.**
Любой ZSET можно снести и пересобрать из таблицы забегов.
Смена формулы = ночной batch-пересчёт по логам + rebuild бордов.

## 4. Схема данных (скелет)

- `users` — id, oauth-идентичности, created_at
- `sessions` — в Redis (opaque token → user_id, TTL)
- `runs` — user_id, mode, duration/word_count, lang, mods (bitmask), seed,
  dict_hash, score, wpm, acc, raw, tp, score_version, tp_version,
  status (pending/accepted/flagged/rejected), log (bytea, compressed),
  created_at. **Логи immutable.** Позже переезжают в S3-совместимый storage.
- `daily_challenges` — date, seed, mods
- `flags` — run_id, reason, resolved_by — для ручного ревью

## 5. Генерация по сиду

Сервер слова **не генерирует**. Он:

- выдаёт сиды (ranked-раны, daily, будущие матчи);
- **раздаёт словари** — `internal/replay/dicts` теперь единственная их копия
  (во фронте `public/static/languages` больше нет): каталог
  `GET /api/v1/dictionaries` + тело `GET /static/dictionaries/{dictHash}.json`
  с `immutable`-кэшем. Подробности — [`docs/DICTIONARIES.md`](docs/DICTIONARIES.md);
- валидирует `dict_hash` (FNV-1a хэш словаря — считается **тем же бандлом ядра
  в goja**, никогда не переписывается на Go);
- при replay проверяет, что текст детерминированно совпадает.

Опубликованный `dict_hash` неизменен навсегда: логи забегов immutable, значит
любой старый ран обязан остаться воспроизводимым. Правка выложенного словаря =
новый файл с новым хэшем, а не редактирование старого.

Оффлайн-раны клиент сидит сам; принимать их как unranked
или ranked со строгими эвристиками — решить позже.

## 6. Авторизация

- OAuth: GitHub + Google через `golang.org/x/oauth2` (руками, goth избыточен).
- Opaque session-токен в httpOnly cookie, сессии в Redis.
- **Не JWT**: для одного сервиса не даёт ничего, кроме невозможности отзыва.
- Пароли не хранить; если когда-нибудь — только argon2id из `x/crypto`.

## 8. Не забыть

- **Rate limiting** на POST /runs и auth (Redis, per-user + per-IP) —
  без него античит бессмысленен.
- Планировщик daily challenge — cron-джоба в river.
- Админ-ручка: ревью flagged, shadow-ban.
- Удаление аккаунта (каскад по забегам).
- Бэкапы Postgres с первого дня (pg_dump cron'ом минимум).
- Наблюдаемость отложить: slog + /healthz до первых пользователей.
- Статика (quotes/custom, фиксированный текст): фронт — абстракция
  seeded|fixed в GenerationConfig + quote_id в контексте лога; сервер —
  реестр цитат (ARCHITECTURE.md §4.5) + per-quote лидерборды
  (SCORING_CONCEPT §6). Слот: фаза лидербордов, после goja-воркера.

## 9. Порядок стройки

Каждый этап — рабочий продукт:

1. ✅ auth + приём забегов с хранением логов (без валидации)
2. бакетные score/WPM-лидерборды
3. ✅ replay-воркер (goja) + scoreV1/scoreV2 — docs/REPLAY.md
4. эвристики античита (сверх флагов ядра) + админ-ревью
5. daily challenge
6. TP (rating)
7. match (мультиплеер: комнаты, WS-релей, GhostCore на клиентах)

## 10. Профиль и статистика (фаза после replay-воркера)

Все метрики — производные от таблицы runs (accepted), новой сборки данных нет,
кроме одного счётчика с клиента:

- Heatmap активности: агрегат по date(created_at)
- Общее время набора: сумма финальных t принятых логов
- Начато/закончено: клиент присылает restartsSinceLastSubmit в payload
  завершённого рана; сервер аккумулирует (недосчёт при закрытии вкладки — ок)
- Статистика + фильтры по режимам: запросы по бакет-колонкам runs
- Лидерборды по категориям: бакеты режим×длительность×язык (SCORING_CONCEPT §4)
- Соревновательные поинты: TP (SCORING_CONCEPT §5, отдельная фаза rating)

Эндпоинты: GET /api/v1/profile/{name}/stats, /heatmap, /runs (публичные),
лидерборды — GET /api/v1/leaderboards/{bucket}. Redis ZSET как read-model
появляется здесь (см. §0 — отложенное подключение Redis).

## 11. Модерация и античит-сигналы

- device_fingerprints(user_id, fp_hash, first_seen, last_seen) — visitor_id
  FingerprintJS (OSS), хэшированный; пишется при логине и при POST /runs.
  Мягкий сигнал: связывание мультиаккаунтов/ban-evasion для ручного ревью,
  НИКОГДА не основание автобана.
- bans(user_id, reason, issued_by, expires_at NULL=перманент) — забаненный
  логинится, но раны не принимаются и скрыты из лидербордов.
- Действия админа: скрыть/восстановить ран (runs.status manual-переходы),
  бан/разбан, очередь flagged-ранов из replay-воркера, связанные аккаунты
  по fp_hash. Privacy policy обязана раскрывать сбор отпечатков.
